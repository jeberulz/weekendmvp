## The Problem

No-code automation spent two years onboarding thousands of non-developers onto AI agent platforms. Marketers, operators, and consultants build agents on Lindy, Relay, and n8n that handle leads, scheduling, and routine ops. The agents work, until they break.

When they break, the error log is written by engineers, for engineers. Stack traces, payload references, and HTTP status codes read like a foreign language to the operator who built the workflow. The person responsible for fixing the agent is the one person who cannot read what went wrong. So the agent sits broken, leads go unhandled, and the operator either pings a developer friend or rebuilds the whole thing from scratch.

This is the new normal. Vibe coding and no-code agents let anyone ship automation fast, but the moment something fails, the gap between building and debugging swallows the project. The failure is rarely complex. It is usually an expired API key or a mismatch between two steps. It just does not read that way.

## The Solution

Doctor Debug catches the failure and reframes it. A user connects an agent once, and Doctor Debug watches each run in real time through the platform webhook and observability APIs. When the agent breaks, an explanation arrives in everyday language alongside a fix path that requires zero documentation reading.

An expired API key reads as an expired API key, with the renewal steps. A malformed output reads as a mismatch between two workflow steps, with the exact line to adjust. Pattern recognition gets sharper as more agents are watched, because the fix library grows from real resolutions rather than synthetic test cases. The operator gets unstuck in minutes instead of waiting on a developer who may never reply.

**How it works:**

1. Integrate one platform first (Lindy) via its webhook and observability API, and ingest a real failure event into a normalized error shape.
2. Build the translation engine: map the error signature to a plain-English explanation plus a ranked fix path, using Claude over a growing pattern library.
3. Ship a dashboard and Slack alert that fire the explanation the moment an agent breaks, with a one-tap was-this-fix-right feedback loop.

## Recommended Tech Stack

The build is an integration plus a translation layer, not new infrastructure. Start with one platform to keep the error-shape mapping tractable, and grow the fix library from real user feedback.

- **Platform webhooks + observability APIs** (Ingestion) — Captures failure events from Lindy and n8n without asking the user to touch code.
- **Claude + a growing pattern library** (AI) — Maps an error signature to a plain-English cause and a ranked fix path, improving as resolutions accrue.
- **Cloudflare Workers + Supabase** (Backend) — Cheap, fast event handling and storage for runs, patterns, and feedback.
- **Web dashboard + Slack alerts** (Delivery) — Meets operators where they already watch for problems and notifies the moment an agent breaks.

**1. Project Setup**

```text
Build the weekend MVP of "Doctor Debug": when an n8n workflow fails, its error is sent to a webhook here and comes back as a plain-English explanation and numbered fix steps that a non-developer can follow. One platform first.

Stack: Next.js (App Router, TypeScript), Tailwind, Supabase (Postgres, Row Level Security, Auth with email magic link), the Anthropic API for the explanation. Tables (Row Level Security on, each user reads only their own projects and events; the webhook writes through the service role):
- projects(id, user_id, name, webhook_secret)
- error_events(id, project_id, platform, step, error_type, message, occurred_at, signature, explanation jsonb, source)  source is pattern or model
- patterns(id, signature, explanation, cause, fix_steps jsonb, confidence, confirmations, rejections, vetted boolean)
- feedback(id, event_id, verdict, correction)

Screens: /login, /projects (create one and copy its webhook and the n8n setup steps), /events (failures with their explanation), /patterns (the library).
Env vars (names only): NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY (server only), ANTHROPIC_API_KEY.

Do not build: billing, plans or an agency tier, other platforms or Lindy, Cloudflare Workers, Slack alerts, a comparison with log tools.
Done when: npm run dev starts, you can sign in, and the four tables exist with Row Level Security on.
```

**2. Core Feature**

```text
Build the one feature that proves Doctor Debug: the same error is explained clearly, and once the fix is confirmed the model is no longer needed.
1. POST /api/hooks/[projectId] takes the n8n error payload with the project's secret in a header and rejects a bad secret. Normalize it to { platform, step (the node name), error_type, message, occurred_at }.
2. Compute a signature from the platform, the error type and the message with numbers, ids, addresses and emails removed, hashed. Save the event.
3. Look the signature up in patterns. Use a pattern that is vetted, or has at least 2 confirmations and a confidence of 0.7 or more. Then no model call happens and the event's source is pattern.
4. Otherwise redact secrets from the message first (anything that looks like a key, a token or an email), then ask the Anthropic API for JSON { explanation: one sentence a non-developer understands, likely_cause: string, fix_steps: string[] of 2 to 6 steps }. Reject an answer outside those limits and show the raw message with a plain note.
5. /events shows each failure with the explanation, the likely cause, the numbered steps and a "Was this right?" control. Yes promotes or strengthens the pattern: confidence is confirmations plus 1 over confirmations plus rejections plus 2. No saves the correction text and counts a rejection.
6. /patterns lists the library with confirmations and rejections so a person can mark one vetted.
Rules: never send a credential to the model. Never invent a platform setting; if the cause is unclear say so. A rejected pattern is never used until it recovers.
Empty state: with no events, show the webhook URL and a sample payload to test with.
Done when: a sample n8n failure is explained with numbered steps, the same error twice produces a pattern after two confirmations and then no model call, a key in the message never reaches the model and a bad secret is rejected.
```
