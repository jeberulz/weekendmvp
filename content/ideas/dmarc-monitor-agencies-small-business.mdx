## The Problem

Web agencies, IT freelancers and small-business owners routinely inherit responsibility for email authentication because they control DNS, maintain the website or administer Microsoft 365. They may not operate the mail infrastructure, understand every sending service or have a dedicated email administrator. When messages begin landing in spam, a client expects the technical contact to explain why. The available evidence often arrives as XML reports, unfamiliar source addresses, alignment results and policy terminology rather than a direct diagnosis.

Even the purpose of DMARC can remain unclear after SPF and DKIM are working. A self-hoster asks what benefit DMARC adds on top of those controls ["I am self-hosting my (secondary) email and have only implemented SPF and DKIM. This works fine on a practical level for me. What would be the benefit of setting up DMARC on top?"](https://news.ycombinator.com/item?id=49081783). That uncertainty matters because an operator may publish a record without understanding reporting, alignment or how policy changes affect legitimate senders. Fragmented software makes the task harder. One practitioner describes ticketing and marketing platforms that misunderstand SPF, DKIM and DMARC ["I have dealt with so many ticketing systems and marketing platforms that do not understand the roles of SPF/DKIM/DMARC at all."](https://news.ycombinator.com/item?id=40708476). A domain may therefore involve a mailbox provider, website forms, a help desk, invoicing software and a campaign platform, with no shared owner of authentication.

The visible symptom is often vague and urgent. A company encountering Microsoft 365 delivery trouble suspected a keyword blacklist ["The company I work for (25friday.com) has been hit with what seems to be a keyword blacklist on Microsoft 365 email."](https://news.ycombinator.com/item?id=43829927). Without a clear workflow, the responsible freelancer may check DNS records, search blocklists, inspect headers and contact vendors without knowing which signal matters. Passing raw DMARC dashboards to the client does not resolve the communication problem. The buyer needs a prioritized explanation: which sender is failing, whether it appears legitimate, what DNS or platform setting should change and how to confirm that the repair worked.

Agencies face an added portfolio burden. Every client can use a different registrar, DNS host and sending stack. The operator needs separation between domains, a record of approvals and a concise status update that can be forwarded without rewriting protocol output. The core pain is therefore not simple report collection. It is converting scattered authentication evidence into a safe action and a credible client explanation before deliverability trouble damages confidence.

## The Solution

MailPlain would be a per-domain DMARC monitoring service designed around diagnosis and communication rather than protocol dashboards. Its wedge is a plain-English issue feed that identifies the likely sending service, explains the authentication failure, proposes the exact DNS or platform change and shows how the operator can verify the result. The interface would prioritize actionable exceptions while keeping raw evidence available for technical review.

A user would connect a domain by publishing or updating a reporting address. MailPlain would ingest aggregate reports, normalize sender sources and correlate them with SPF, DKIM, alignment and current DNS records. Recognizable services would appear under human-readable labels. Unknown sources would enter a review queue where the user can mark them as approved, suspicious or needing client confirmation. Each diagnosis would include context about likely impact and a remediation checklist suited to the relevant DNS or sending provider.

For agencies, the product would add portfolio triage and client communication. A shared dashboard would show domains needing action, domains awaiting approval and domains that appear stable. A client-ready summary would explain the problem, recommended fix and observed result without exposing unnecessary XML detail. Approval links would let the client confirm a sender or authorize a proposed DNS change while leaving publication under the operator's control.

MailPlain should initially remain advisory. It can generate copyable record values, preserve previous configurations and monitor the effect of a change, but it should not silently edit production DNS. That boundary supports trust while the product learns how varied sender stacks behave. Over time, provider integrations can streamline implementation after the diagnosis, approval and verification loop is reliable.

The workflow below is MailPlain's proposed first version: a plan to build, not a tested product.

**How it works:**

1. **Connect Domain** — The user adds a domain, confirms the reporting destination and follows provider-specific instructions for routing aggregate reports. MailPlain inspects the current SPF, DKIM and DMARC posture, maps visible senders and highlights configuration gaps without requiring the user to interpret raw XML.
2. **Understand Senders** — MailPlain groups authentication traffic by recognizable service, domain alignment and outcome. Instead of exposing protocol-heavy tables as the main interface, it explains which system appears legitimate, which source needs investigation and why a failure may affect trust or delivery.
3. **Apply the Fix** — For each issue, MailPlain proposes a plain-English remediation path with the exact DNS record change, expected effect and rollback guidance. The user can copy a provider-ready value, request approval from a client and record when the change was published.
4. **Prove the Result** — After a change, MailPlain watches subsequent reports for alignment improvement, unexpected senders and policy impact. It creates a concise client summary showing what changed, what remains unresolved and which action deserves attention next, while retaining an audit trail for the agency.

What not to build yet (scope advice for MailPlain's first version, not research):

Do not build a full outbound email platform, blacklist removal service or autonomous DNS writer before the monitoring and guided-remediation workflow earns trust.

## Recommended Tech Stack

A suggested stack for MailPlain (a recommendation, not research):

Use a TypeScript application with Next.js for the dashboard and API routes, PostgreSQL for normalized authentication data, and a durable object store for original aggregate report files. A background queue should parse XML, enrich source addresses, refresh DNS records and generate summaries without blocking the interface. Isolate report ingestion from customer-facing requests, validate archive contents defensively and preserve parser errors for review. Add encrypted credentials for provider integrations, role-aware client approvals, immutable DNS change snapshots and structured observability around delayed reports, duplicate payloads and sender classification decisions.

- **Next.js + TypeScript** — screens for Connect Domain, Understand Senders, Apply the Fix, Prove the Result
- **Postgres (Supabase or Neon)** — monitored\_domains, aggregate\_reports, sender\_sources, remediation\_actions, client\_approvals, domain\_snapshots
- **Auth (Clerk or Supabase Auth)** — workspace seats and roles
- **Stripe Billing** — Solo Domain / Client Desk / Agency Portfolio subscriptions
- **Vercel** — previews and production
