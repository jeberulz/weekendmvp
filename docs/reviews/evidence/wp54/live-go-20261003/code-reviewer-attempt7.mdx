## The Problem

Indie developers and small engineering teams face an awkward consequence of faster code generation: producing a change can become easier while validating that change remains slow. A community account describes higher pull request volume from AI-generated code without a matching improvement in review time, turning review into the main bottleneck ["We’re seeing much higher PR volume from AI-generated code, but review time hasn’t improved, so PR review has become the main bottleneck instead of coding."](https://news.ycombinator.com/item?id=48329446). For a GitHub maintainer who is also writing features, handling support, and operating production, that bottleneck competes directly with product work.

Current AI review does not automatically solve the problem because attention is scarce. If a bot posts generic advice, misunderstands repository conventions, or treats every possible improvement as a blocker, the maintainer must review the reviewer. A developer who uses AI code review every day reports that its output often does not make sense ["When AI says something - many a time, it doesnt make sense. And I use AI code review tools every day."](https://news.ycombinator.com/item?id=46348957). Another user describes results as inconsistent, while still valuing the useful hits because misses are cheap to disregard ["Like a lot of my AI experiences it's pretty hit or miss and it's non-deterministic but it doesn't have much cost to disregard the misses and I appreciate the hits."](https://news.ycombinator.com/item?id=46348957). That tolerance can disappear when noisy comments arrive on every active pull request or create confusion for contributors.

Small teams also need AI review to fit their existing process rather than dictate a new one. A team describes using draft pull requests and including AI review before the remaining human review begins ["My team uses draft PRs and goes through a process, including AI review, before removing the draft status thereby triggering any remaining human review."](https://news.ycombinator.com/item?id=46348957). This workflow treats automation as preparation for human judgment, not a replacement for it. The product opportunity is therefore about triage and context: catch plausible defects, explain meaningful risk, and leave architecture, intent, and tradeoffs to people.

Established products demonstrate that buyers already encounter paid per-user packaging. Greptile offers a Pro plan [$30/user/month (Greptile Pro plan)](https://www.greptile.com/pricing), while CodeRabbit sells several plans including Essentials [$24/user/month, billed annually (CodeRabbit Essentials plan)](https://docs.coderabbit.ai/management/plans), Team [$48/user/month, billed annually (CodeRabbit Team plan)](https://docs.coderabbit.ai/management/plans), and Advanced [$72/user/month, billed annually (CodeRabbit Advanced plan)](https://docs.coderabbit.ai/management/plans). The gap is not the absence of AI reviewers. It is the need for a quieter, easier-to-configure reviewer whose cost and workflow fit indie maintainers and compact GitHub teams.

## The Solution

MergeSift is a GitHub App that reviews pull requests before scarce human attention is spent. Its wedge is repository-aware triage for indie developers and small engineering teams: identify changes that plausibly affect correctness, security, reliability, or established project rules, then keep lower-value observations out of the main review path.

Installation should require selecting repositories and granting the minimum practical GitHub permissions. MergeSift would read contribution guidance, repository structure, test patterns, ownership signals, and maintainer-approved rules. When a pull request changes, it would analyze the diff with nearby code and relevant repository context. Findings would be ranked by likely impact and confidence rather than published as an undifferentiated list.

The GitHub experience would center on concise inline findings and a summary check. Each surfaced concern would explain what changed, why it might matter, and what evidence in the repository informed the assessment. Merge concerns would be separated from optional follow-up ideas, allowing authors to resolve important issues without debating minor suggestions. Uncertain architectural questions would be routed to humans rather than framed as authoritative defects.

The learning loop is central to the product. Maintainers could dismiss a finding with a reason, approve a useful rule, or mark an observation as irrelevant for that repository. MergeSift would adapt future review behavior while preserving visible policy controls. Over time, the product should become quieter and more specific to the codebase. The outcome is not autonomous approval. It is a prepared pull request in which routine risks have been screened and human reviewers can focus on architecture, intent, and whether the change makes the product better.

The workflow below is MergeSift's proposed first version: a plan to build, not a tested product.

**How it works:**

1. **Repository Context** — After installation, MergeSift would map repository structure, contribution guidance, ownership patterns, test conventions, and selected pull request history. Maintainers could approve the inferred context and add plain-language rules so reviews reflect local engineering expectations rather than generic style preferences.
2. **Risk Triage** — When a pull request opens or changes, MergeSift would inspect the diff alongside relevant files and configured policies. It would group potential findings by impact, suppress repetitive style observations, and identify uncertainty before deciding whether a comment deserves developer attention.
3. **Review Delivery** — MergeSift would publish concise GitHub comments attached to the relevant lines, explain the likely consequence, and suggest a practical correction when appropriate. A summary check would separate merge concerns, follow-up ideas, and areas that still require architectural judgment from a human reviewer.
4. **Learning Loop** — Developers could mark findings as useful, incorrect, irrelevant, or already understood directly in GitHub. MergeSift would use that feedback to adjust repository-specific preferences, surface recurring policy gaps, and reduce comments that the same team repeatedly dismisses.

What not to build yet (scope advice for MergeSift's first version, not research):

Do not build a broad application security suite, autonomous merge agent, or general engineering analytics platform yet.

## Recommended Tech Stack

A suggested stack for MergeSift (a recommendation, not research):

Build MergeSift as a GitHub App with a TypeScript service handling installation events, pull request webhooks, check runs, and inline review comments. Use Postgres for repository policies, review state, findings, and feedback. Queue analysis jobs so webhook responses remain fast and duplicate events are idempotent. A diff parser should select relevant context before model calls, while a policy engine filters low-confidence findings. Encrypt installation credentials, minimize retained source content, record review provenance, and provide deletion controls for repository owners.

- **Next.js + TypeScript** — screens for Repository Context, Risk Triage, Review Delivery, Learning Loop
- **Postgres (Supabase or Neon)** — github\_installations, tracked\_repositories, pull\_request\_reviews, review\_findings, repository\_policies, finding\_feedback
- **Auth (Clerk or Supabase Auth)** — workspace seats and roles
- **Stripe Billing** — Open Source Maintainer / Solo Repository / Pull Request Crew subscriptions
- **Vercel** — previews and production
