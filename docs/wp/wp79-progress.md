## 2026-11-06 — Persisted D5 retention queue proposed (schema only)

- Add `lead_retention_jobs`, one transactional upsert per archived project, with required `ownerId`, `projectId`, `archivedAt`, immutable-by-runtime `deleteDueAt = archivedAt + 30 days`, separate `nextAttemptAt`, explicit `scheduled|complete|cancelled` state, attempt/progress counters and timestamps. Index by project for uniqueness checks, owner/project for authorization, and `(state,nextAttemptAt)` for a bounded due scan. Retry backoff must move only `nextAttemptAt`; an error keeps the job scheduled and raises an alarm rather than entering a terminal blocked state.
- Archive must atomically set the project timestamp and upsert/reschedule its job with `nextAttemptAt = deleteDueAt`; unarchive atomically clears the timestamp and cancels an unprocessed job; rearchive gets a new deadline. Account closure must archive owned projects through a bounded, resumable cursor before completion. No archive/unarchive/closure runtime exists in this schema slice. A future **at least hourly** cron will process a fixed-size due page, then one bounded lead revocation/deletion transaction at a time for real leads, or WP78's existing 50-row synthetic purge. `deleteDueAt` remains visible for overdue alarms while retries move only `nextAttemptAt`. The persisted queue survives a backup restore and can resume by index without a recurring global project scan.
- No `projects.by_archivedAt` index is added. A one-time owner-run migration for any pre-existing archived projects must paginate projects by creation order, inspect `archivedAt`, and idempotently upsert missing due jobs. It needs backup, dry-run inventory, exact target and owner approval before production; it can restart from null safely. This is a future migration gate, not a live backfill in this PR. WP78 real capture remains off until archive hooks, cron, per-lead revocation, privacy notice and opt-in are integrated.
