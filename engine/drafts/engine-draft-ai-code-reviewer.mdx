## The Problem

Indie developers and engineering leads on sub-10 GitHub teams are encountering a new throughput mismatch. AI coding assistants let authors create more code, larger changes, and sophisticated implementations faster, but the team’s ability to verify that output has not expanded at the same rate. The burden falls disproportionately on senior developers, maintainers, and technical founders who already own architecture, production reliability, and mentorship.

Traditional pull-request heuristics become less reliable when code is generated in large chunks. A reviewer may recognize a teammate’s habits, infer intent from commit progression, and know where that developer commonly makes mistakes. AI-generated code lacks those familiar signals. It can look polished while taking an unnecessarily general approach, introducing subtle edge cases, or following patterns that do not fit the repository. Reviewers must reconstruct the implementation story before deciding whether the change is safe.

Existing AI reviewers do not automatically solve the capacity problem. Community participants describe them as linter-like: they flag potential problems, but humans still have to validate every comment. Speculative findings can send less-experienced developers into unproductive investigations, while a long list of minor observations obscures the one issue that matters. The bot then becomes another pre-review gate, adding latency before the pull request reaches a human.

The operational cost is visible in growing queues and reduced senior focus. One engineer reports reviewing 47 pull requests in a week on a team of 8. Another estimates spending 60% of working time reviewing pull requests and only 25% writing code. That shift also damages mentorship. Senior developers have less time for architecture discussions and pair programming, while junior developers receive terse asynchronous corrections without learning the reasoning behind them.

The buyer therefore does not primarily need more comments. A technical founder, lead engineer, or open-source maintainer needs faster confidence: a concise explanation of what changed, a prioritized view of meaningful risk, and evidence that each flagged issue fits the repository’s actual behavior. The product must reduce verification work without encouraging blind trust or pretending business context can be inferred perfectly.

## The Solution

ReviewLoom is a precision-first GitHub reviewer built for Indie developers and sub-10 engineering teams. Its wedge is a low-noise sanity check: instead of covering a pull request with every plausible concern, it produces a semantic change brief and publishes only evidence-backed findings that cross a configurable confidence threshold.

After installation, ReviewLoom builds repository memory from accepted code, tests, configuration, contribution guidance, and prior review outcomes. When a pull request opens, it maps changed files into behaviors and data paths, identifies where the implementation diverges from established patterns, and explains the likely story of the change. Candidate findings are checked against repository context and deterministic signals before appearing in GitHub. Each published finding states its severity, evidence, affected behavior, and a focused verification path.

The initial product should optimize for reviewer attention rather than autonomous merging. Authors can use the brief before requesting human review, while senior developers can begin with the highest-risk areas instead of reconstructing the entire diff unaided. Confirmed and dismissed findings become repository-specific feedback, allowing ReviewLoom to learn that a pattern is intentional without applying that preference universally.

The Open Source tier provides free review for eligible public repositories, generating visible examples of useful output and attracting maintainers. Indie supports private repositories for solo developers and very small teams. Crew adds shared review policies, repository-level analytics, and deeper memory for teams that need consistent standards. The promise remains intentionally narrow: fewer distractions, clearer implementation context, and more senior engineering time reserved for architectural and business decisions.

**How it works:**

1. **Repository Memory** — ReviewLoom installs as a GitHub App and indexes approved code, tests, configuration, contribution guidance, and recurring reviewer decisions. It builds a compact repository profile so findings reflect local conventions and architecture instead of generic programming advice.
2. **Semantic PR Map** — For each pull request, ReviewLoom groups changed files into behaviors, dependencies, data paths, and likely intent. The resulting review brief explains what changed, where risk concentrates, and which unfamiliar patterns deserve human attention before inline comments appear.
3. **Evidence-Gated Findings** — Candidate issues are checked against repository context, changed tests, deterministic analysis, and confidence thresholds. ReviewLoom publishes only prioritized findings labeled by severity and evidence, suppressing speculative observations that would force developers to investigate low-value possibilities.
4. **Human Learning Loop** — Authors and reviewers can confirm, dismiss, or clarify every finding directly in GitHub. ReviewLoom records those outcomes as repository-specific decisions, improving future prioritization while preserving an audit trail that explains why recurring patterns are accepted or rejected.

Do not build autonomous merge approval or a full replacement for human architectural review yet.

## Competitive Landscape

CodeRabbit is the closest commercial benchmark, with contributor-based pricing, multiple capability tiers, and free open-source access. Graphite combines AI review with a broader pull-request workflow and offers seat-based plans, including unlimited AI reviews on its Team plan. Qodo uses pooled credits, which gives teams usage flexibility but introduces another quantity to forecast.

ReviewLoom should not try to beat these products by generating more comments or immediately matching every workflow feature. Its differentiation is disciplined omission. It is designed for Indie developers and sub-10 teams that need a sanity check rather than an enterprise review platform. Every review begins with a semantic implementation brief, and inline findings must carry repository-specific evidence and pass confidence thresholds. Confirmations and dismissals become local review memory, helping the system suppress repeat noise. Simple per-developer pricing also avoids Qodo-style credit calculations, while the Open Source tier creates public proof that ReviewLoom can identify consequential issues without overwhelming maintainers.

## Recommended Tech Stack

Build ReviewLoom as a GitHub App receiving pull-request, review, and push webhooks through a typed API service. Use a job queue to clone only required commits, parse diffs, run language-aware static checks, and assemble bounded repository context. Store embeddings and repository decisions separately from source snapshots, with encryption and explicit retention controls for private code. A model-routing layer should separate semantic summarization from higher-cost finding verification. Post check runs and review comments through idempotent workers, and retain the evidence, confidence, model version, and user disposition behind every published finding.

- **Next.js + TypeScript** — screens for Repository Memory, Semantic PR Map, Evidence-Gated Findings, Human Learning Loop
- **Postgres (Supabase or Neon)** — repositories, pull_requests, review_runs, findings, finding_feedback, repository_decisions
- **Auth (Clerk or Supabase Auth)** — workspace seats and roles
- **Stripe Billing** — Open Source / Indie / Crew subscriptions
- **Vercel** — previews and production
